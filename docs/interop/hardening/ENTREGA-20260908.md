## Executar no Linux

Extraia o ZIP em uma pasta nova, entre em `dom-protocol` e execute:

```bash
python3 scripts/test_interop_hardening.py --format --mode full
```

Esse comando primeiro aplica rustfmt (a ferramenta também não está disponível
no ambiente de geração), depois executa as suítes. Exige Git, Python 3, Rust/Cargo
com rustfmt, compilador C, clang, cmake, pkg-config, Bitcoin Core, Foundry, Anvil
e curl instalados. Não instala ferramentas, não publica no GitHub, não faz
commit, não transmite em mainnet e não acessa sua wallet. Os scripts existentes
iniciam suas próprias redes de teste. As dependências Cargo precisam estar em
cache ou acessíveis pela rede. Use a versão Rust aprovada pelo projeto; o novo
job reutiliza a versão `1.96.1` já fixada no F5.

Para executar os componentes sem Bitcoin Core/Foundry:

```bash
python3 scripts/test_interop_hardening.py --format --mode components
```

`components` não equivale a `full`. O relatório identifica o modo. Ambos incluem
BTC crypto/rounds/actuator, adapters Solana, programa Solana standalone e
`dom-interopd` com `--no-default-features --features production --lib --tests`.
`full` acrescenta o regtest Bitcoin existente, contratos no perfil `deep` e o
harness Anvil existente, sem filtro de cenários.

Logs e `report.json`: `artifacts/interop-hardening/<execução>/`. O relatório
registra exit code, duração e SHA-256 de cada log, branch, commit-base e hash do
conteúdo antes/depois da execução. Exit 2 indica ferramentas ausentes; exit 1
indica falha de comando; exit 0 indica conclusão dos comandos daquele modo.
Nenhum desses resultados é uma medida de probabilidade de perda de fundos.

A pasta `.git` está incluída para preservar a branch e a base. As alterações
estão no índice/working tree, sem novo commit ou push; os metadados de autoria
serão definidos no seu ambiente. `git diff --cached` mostra a entrega original;
após rustfmt, `git diff` também mostrará os ajustes locais de formatação.
O clone contém o histórico raso disponível, não todas as branches históricas.

### Regressões adicionadas/adaptadas

- SOL: doação antes do funding ainda exige pagamento integral do funder.
- SOL: doação depois de funding, claim/refund, excedente grande, principal exato e replay terminal.
- SOL: shortfall e sweep antes do terminal recusados sem movimentação.
- SOL: Close não destrói o recibo; sweep repetido/doação posterior conserva recibo byte a byte.
- SPL: funding/claim/refund/sweep passam pelo processor real do Token Program no harness host.
- SPL: shortfall, mint incorreta e beneficiário incorreto recusados antes de pagamento.
- Wire V2: namespace separado, versões/tags/bytes extras recusados.
- Observer: initialize+fund gerados pelo client, ordem de contas, ambiguidade e substituições.
- BTC: buffer remoto alterado após verificação não altera a pré-assinatura agregada.
- Tempo: refund após expiração continua autorizado; relógio zero/regressivo não alcança a autoridade de planos.

O harness host emula o System Transfer e o despacho de CPI, incluindo a assinatura
PDA; ele não emula rollback transacional completo nem prova execução de binário SBF.
Essas limitações constam também no cabeçalho dos testes.

## Compatibilidade Solana

O programa foi elevado de 0.1.0 para 0.2.0. O layout de state e as instruções
operacionais V1 permanecem, mas Close agora retorna `StateRetentionRequired=18`.
O namespace adicional `DOMSLIX2`, versão 2, tag 1, codifica exclusivamente
`SweepTerminalExcess`; o decoder V1 o recusa. Os valores são código candidato,
não uma alegação de ratificação normativa. Sweep não aceita montante livre.

A rent de state e vault permanece retida. O excedente vai somente ao funder;
para SPL, a conta de destino deve ter mint correta e owner igual ao funder.
O status, segredo público e slot terminal não são regravados pelo sweep.

O ID de programa existente foi preservado para compatibilidade dos testes locais.
Este ZIP não altera um programa já implantado. Um programa imutável antigo não
passa a executar o novo código. A ativação exige um deployment permitido pelo
modelo de autoridade existente, ID/codehash e registry/profile correspondentes.
Operações antigas continuam exigindo a semântica e o deployment originais.
A rota Solana continua bloqueada no production root existente.

## Trabalho ainda não implementado nesta entrega

- C05: composição completa Bitcoin/M.8, wire autenticado entre participantes e instalação de claim no root. O `materialization_scope: None` do construtor concreto permanece; não foi preenchido artificialmente para liberar funding.
- C07: instalação tardia/restauração da fonte pública EVM no root.
- C08: nova campanha de vinculação contextual DLEQ na integração. A criptografia não foi redesenhada.
- C09: política completa de ativos/RPC e autoridade econômica XMR.
- C11: matriz multichain pelo daemon real, fault injection e oráculo econômico independente. O executor de suítes entregue não substitui essa matriz.
- C12: deploy reproduzível, auditoria externa, revisão criptográfica e recuperação operacional independente.
- Meta 10/10: verificação formal conectada à implementação e auditorias independentes não foram realizadas.

Esses itens impedem afirmar que o protocolo inteiro está pronto para fundos reais.
SOL/XMR não foram habilitados e não foi criada nenhuma pré-assinatura fictícia,
chave compartilhada artificial ou autorização que retorne sucesso sem validação.
